# 我的任务页面规格文档 (Spec)

## 1. 页面概述
“我的任务”是集采工作台的核心办理入口，统一承载了检查执行、不合规处置、整改复核和申诉处理任务。

## 2. 页面布局
- **整体框架**：使用 `CentralizedProcurementLayout` 通用布局。
- **顶部区域**：列表视图展示面包屑导航（首页 / 招标采购 / 一单一检 / 我的任务）；办理视图展示任务详情面包屑和顶部操作栏。
- **页签切换**：顶部设置“自查任务”、“互查任务”、“稽查任务”三个页签；每个任务页签下方提供“全部、待检查、待复核、待整改、待处理申诉”二级页签。
- **搜索筛选区**（页签维度隔离）：
  - 筛选条件现在位于每个页签的内容区域内，不同页签拥有独立的搜索状态和筛选结果。
  - 查询与重置按钮独占筛选区末行，并靠右排列。
  - 任务搜索：模糊搜索任务编号。
  - 任务状态：按当前任务类型提供对应状态，避免自查、互查、稽查状态交叉展示。
  - **招标/采购编号**：支持输入检索。
  - **招标/采购名称**：支持输入检索。
  - **合同名称**：支持输入检索。
  - **合同编号**：支持输入检索。
  - 更新时间：起止日期范围选择（已汉化，支持中文占位符和本地化显示）。
  - **自查互查结论**：仅稽查任务提供“一致 / 不一致”筛选条件，用于筛选前序自查与互查结论比对结果；选择后立即生效，无需再次点击查询。
- **列表展示区**：使用 Ant Design Table 展示任务列表，设置横向滚动条以保证大量列宽度展示完整，支持操作列固定在右侧。
- **分页区**：底部展示分页控件。

## 3. 核心功能点
- **页签隔离**：不同页签（自查/互查/稽查）的筛选条件、搜索状态和二级页签状态完全隔离，切换页签时保留各自的筛选结果。
- **二级页签筛选**：待检查筛选“待处理、检查中”任务；待复核筛选“待复核”任务；待整改筛选“待处置、复核不通过”任务；待处理申诉筛选“申诉中”任务。筛选范围始终限定在当前的自查、互查或稽查任务类型内。
- **身份隔离**：根据当前登录用户的业务身份展示对应的页签和任务。
- **任务列表字段**：
  - **序号**：`render: (text, record, index) => index + 1`，自增列。
  - **自查互查结论**：仅稽查列表展示，位于序号列后，标识“一致”或“不一致”。
  - **督办标识**：仅稽查列表展示，位于序号列后；当自查与互查结论不一致且高风险项超过 3 项时，自动标记“稽查优先督办项”并置顶。
  - 任务编号
  - 任务类型（自查/互查/稽查）
  - **招标/采购编号**：例如 `cscec202608310000004851`（样式契合业务场景）。
  - **招标/采购名称**：对应招标项目名称。
  - **合同名称**：原合同信息拆分。
  - **合同编号**：原合同信息拆分。
  - **评审完成时间**：例如 `2026-08-31 15:00:00`。
  - 当前状态：使用 PRD 状态总表的完整状态名称，例如自查待处置、互查待复核、稽查复核不通过。
  - **判定结果**：尚未提交检查的待处理、检查中、回退审批中和已收回任务展示 `-`；检查提交后按首次检查结论展示“合规”或“不合规”，后续整改、复核和申诉不会覆盖首次检查结论。
  - **整改结果**：首次检查尚无结论或结论合规时展示 `-`；首次检查不合规且任务尚未闭环时展示“未整改”，任务进入对应“已自查 / 已互查 / 已稽查”完成状态后展示“已整改”。
  - 待本人处理事项
  - 问题统计（不合规项数量）
  - 检查剩余时限：仅“待处理”“检查中（自查中、互查中、稽查中）”“回退审批中”状态展示检查办理倒计时；申诉中及其他状态显示 `-`。临近时限任务以橙色显示并标记“临近超时”，不展示“已超时”标签。
  - **操作**：支持固定在右侧（`fixed: 'right'`），状态驱动展示检查、整改、复核或查看。
- **操作逻辑**：
  - 自查、互查、稽查的待处理和进行中状态展示“检查”，进入检查执行模式。
  - “检查”办理视图右上角提供“申请回退”按钮，与保存草稿、提交检查并列展示；点击后提交当前任务的回退申请。
  - 待处置、复核不通过状态展示“整改”，供合同经办人处理不合规检查项。
  - 任务信息展示检查人信息、检查完成时间及申诉倒计时。接收到含不合规项的检查结果后，自检查完成时间起3天内可发起申诉；倒计时按秒实时刷新，超过3天显示“已超过3天，不可申诉”并禁用“申诉”按钮。
  - 整改办理视图顶部同时提供“申诉”按钮；点击后切换为申诉办理状态，检查项表格前方出现复选框，并在基础检查信息后展示“第1轮申诉说明”“申诉附件”两列。申诉说明和附件仅对不合规检查项开放填写与上传；仅不合规检查项可勾选申诉。
  - 申诉办理状态下，顶部主按钮由“提交整改”变为“提交申诉”，并提供“退出申诉”按钮以返回整改办理。复选框仅决定检查项是否纳入本次提交。提交前必须至少勾选一项，申诉说明和申诉附件均为选填。提交后任务状态更新为对应类型的“申诉中”，同时写入申诉提交流转记录。
  - 待处理申诉页签中的申诉中任务，操作展示“处理申诉”；局管理员可查看已提交的第1轮申诉说明和附件，并逐项选择“通过”或“不通过”。申诉不通过时必须填写处理意见；全部处理后，申诉通过项视为合规并跳过整改，申诉不通过项保持不合规并进入整改；任务只要存在不通过项就转为待处置，否则任务闭环。
  - 申诉结果完成后，整改办理和复核办理均按检查项过滤：申诉通过项只读展示，不要求整改或复核；申诉不通过项由合同经办人提交整改材料，再由原检查人进行复核。问题统计只统计仍需整改的不通过项。
  - 待复核状态展示“复核”，供原检查人逐项复核整改材料。
  - 其他状态展示“查看”，以只读方式查看任务记录。
  - 点击操作后在当前页面切换至任务办理视图，使用当前任务的 `taskId` 和 `mode` 状态展示对应的检查、整改、复核或查看内容；返回任务列表后保留原任务列表的页签和筛选状态。
  - 办理视图保留原任务执行页的任务信息、检查项处置明细、保存草稿、提交校验和任务流转记录。
  - 检查执行表第一列展示连续序号，随后展示检查阶段、检查项、检查方式和检查标准；检查阶段沿用模板管理的“招标/采购阶段 - 子阶段”“合同阶段”设置。
  - 检查详情的明细表格上方展示综合“判定结果”。检查办理未完成全部系统识别和人工判定时展示“待判定”；提交后综合检查项原判定与申诉结果，任一仍有效的不合规项则展示“不合规”，申诉通过项按“合规”计算。
  - 检查方式区分“系统识别”和“人工检查”。进入检查后，系统识别项初始展示“待计算”，检查人点击“计算系统识别项”后，所有系统识别项统一进入“计算中”，计算完成后自动展示系统判定及识别说明；系统识别项不可人工选择合规或不合规。
  - 人工检查项由检查人选择“合规”或“不合规”并填写备注、上传附件；提交检查前，必须已完成系统识别计算及全部人工检查项判定。
- **同一招标的阶段复用**：同一招标可关联多张合同单据，招标阶段检查项仅由首位检查人执行一次。后续合同检查人进入“检查”后，页面顶部先展示只读的“招标阶段检查项（已完成）”表格，包含检查结果、备注、附件、检查人和检查时间；下方仅展示可编辑的“合同阶段检查项”，提交校验也只覆盖合同阶段的待办项。
- 稽查任务进入“检查”执行模式时，按“自查检查数据（只读）”“互查检查数据（只读）”“稽查检查数据”顺序展示三个独立表格。前两张表展示同一业务单已完成的前序检查结果、备注和附件，仅供稽查人员查阅，不提供计算、判定、备注编辑或附件上传入口；稽查检查数据表沿用正常检查流程，可计算系统识别项并编辑人工检查项。
  - 待复核任务必须预置第一轮整改说明、整改材料和“待复核”状态；办理表格完整展示第一轮整改信息，并在对应的第一轮复核判定结果列提供“通过 / 不通过”选择和复核意见输入。
  - 提交复核前，所有“待复核”的检查项均须完成复核判定并填写复核意见；已完成或非不合规检查项保留只读展示。

## 4. 视觉风格
- 遵循集采工作台统一视觉规范。
- 临近时限任务使用橙色文字、图标与“临近超时”标签预警。
- 状态标签使用不同颜色的 Tag 区分。
- 表格支持横向水平滚动以适配宽字段展示（如招标采购编号、评审完成时间、合同编号等）。

## 5. 模拟数据 (Mock Data)
- 更新 mock 结构，提供丰富的真实性数据，包括：
  - `bidNo`: 招标/采购编号
  - `bidName`: 招标/采购名称
  - `contractName`: 合同名称
  - `contractNo`: 合同编号
  - `reviewCompleteTime`: 评审完成时间
  - 其它固有字段（任务编号、任务类型、当前状态、待处理项、问题统计等）。
- 自查、互查、稽查均按各自可办理状态集生成至少一条模拟数据，包含待处理、进行中、回退审批中、待处置、待复核、复核不通过、申诉中和已完成等状态；自查额外覆盖已收回状态。待派发任务不属于“我的任务”页面，不提供对应筛选项或模拟数据。
- 阶段完成状态统一命名：自查完成为“已自查”，互查完成为“已互查”，稽查完成为“已稽查”。
- 稽查任务模拟数据包含自查互查结论比对结果、高风险项数量和优先督办标识；满足“结论不一致且高风险项超过 3 项”的记录自动置顶，并展示“稽查优先督办项”标签。
- 每条任务通过 `transitionRecords` 保存从合同评审完成到当前状态的完整合法状态机路径，包含事件类型、事件说明、流转前后状态、操作人、操作时间、处理意见和关联业务单号；详情页按时间倒序展示。
- 互查任务的流转记录必须先完整经过自查并进入“已自查”；稽查任务必须先完整经过自查、互查并依次进入“已自查”“已互查”，再进入稽查环节，不得只展示当前阶段的派发与处理记录。
- 互查任务的前序自查流转记录仅展示自查检查已提交及后续流程节点，不在检查提交记录中描述最终检查结果是否合规。
- 流转记录严格对应任务当前状态：待处理仅记录本阶段的生成与派发；检查中增加开始处理；回退审批中从待处理或检查中记录回退申请；自查已收回按真实前态依次记录超时提醒与自动收回；整改、复核、申诉状态均以前序不合规检查提交为基础；完成态分别覆盖首检合规完成或问题整改复核通过后的闭环完成。
- 模拟数据仅记录任务生成、派发、开始处理、检查提交、回退申请、超时、自动收回、整改提交、整改复核、申诉提交和问题闭环等关键事件，不记录普通查看、页面访问或草稿保存。
- 检查项模拟数据覆盖模板中的约标阶段、发标阶段和合同阶段，并至少包含一条系统识别的采购项目关联性检测项。
- `TASK-20260901-002` 包含两条系统识别项及两条人工检查项，覆盖采购项目关联性检测、招标文件发布时限校验、投标人资格条件设置审查和合同关键条款检查。
- `TASK-20260901-002` 模拟同一招标下的后续合同检查：预置首位检查人“李敏（合规专员）”完成的三条招标阶段检查结果及检查时间，当前任务仅需检查合同关键条款。
- 自查、互查、稽查的待复核任务均预置第一轮整改记录，其中至少两条不合规检查项带有整改说明、附件、待复核结果和空白复核意见，以验证复核办理能力。
- 增加合同名称为“模拟申诉通过”的自查整改任务，预置两条申诉记录：一条申诉通过并视为合规，另一条申诉不通过并保留整改待办；明细列表展示申诉说明、申诉附件、第1轮申诉结果和处理意见，整改提交后仅不通过项进入复核。
