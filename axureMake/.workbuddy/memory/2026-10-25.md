## 用 doc/example 两份真实清单验收，并修掉 3 个解析缺陷

**样例**：`doc/example/2、西南分公司-…铝合金踢脚线-采购清单.xlsx`（投标报价表版式，两行表头 + 合并单元格 + `!ref` 到 HV 列）、`doc/example/总需求计划.pdf`（扫描全能王扫描件，1 页，**无文字层**，items=0）。

**发现的真问题**
1. 双行表头：首行是「单价（元）…」合并单元格、次行是「不含税单价/税额/含税单价」，原逻辑把次行当数据行，且空列名生成「列N」。
2. 尾部空列：xlsx `!ref` 到 HV（230 列），预览与 AI 映射请求被 220 个空列污染。
3. 条款行被当物料：合计/质量标准/付款方式/发票税金/供货时间/其它事项/供应商/联系人/签章/报价时间 全部送进模型，产出 55% 置信度的假原子属性。
4. PDF 扫描件：直接抛错，用户卡在第一步无路可走。

**修复**
- `extract.ts`：新增 `trimColumns`（按内容裁列）、`findHeaderRow`（表头关键词评分，避免「项目名称」标题行被当表头）、`looksLikeSubHeader` + `mergeHeaderRows`（合并为「单价-含税单价」）、`shortLabel`（去括号补充）；扫描件不再抛错，返回 `scan: true` 的 text 类型，进入文本录入兜底。
- `decompose.ts`：新增 `NOISE_ROW` 正则 + `isNoiseRow`，`buildRawItems` 改为返回 `{ items, skipped }`，`buildItemsFromLines` 同样过滤；`guessMapping` 改为按别名从具体到宽泛匹配 + 否定词护栏（「含税单价」不再命中「单价-不含税单价」）+ 同分取最短表头。
- `ImportPage.tsx`：扫描件告警 + 粘贴引导；展示「已自动跳过 N 行非物料行」；示例值取首条真实物料行。
- ATOM_SYSTEM 增加归一化硬约束：区间统一 `Φ8~Φ10mm`、「以内」→`≤`、「及以上」→`≥`、「综合」合写牌号、同品类固定属性组、无牌号不猜牌号且整体 ≤70、用途固定枚举。

**验收结果**

## 修复「导出页面报 Failed to fetch code: Internal Server Error」

**现象**：导出 `ai-material-price-governance` 时报 `Failed to fetch code: Internal Server Error`。

**定位链路**：admin 导出走 `fetch(origin + jsUrl)`，`jsUrl = /build/prototypes/<name>.js` → `vite-plugins/virtualHtml/handlers/buildHandler.ts` 用 `npx vite build` + `ENTRY_KEY` 走单入口 iife 构建 → 构建失败即回 500。

**根因**：`ai/extract.ts` 里为懒加载写了 `await import('xlsx')` / `await import('pdfjs-dist')` / `await import('...pdf.worker.min.js?url')`。iife 不支持代码分割（`forceInlineDynamicImportsOff` 让 iife 关闭 inlineDynamicImports），于是 rollup 报 `Invalid value "iife" for option "output.format" - UMD and IIFE output formats are not supported for code-splitting builds`（在 generate 阶段，得等 ~2min 才报，容易被误判为超时）。

**修复**
1. `ai/extract.ts` 改静态导入（单文件 iife 里不存在懒加载的意义）。
2. pdf.worker 由 `?url` 改 `?raw` + `Blob` + `URL.createObjectURL`：`?url` 会产出 `dist/assets/pdf.worker-*.js`（1.09MB > assetsInlineLimit 1MB），而 `/build/` 只回主 JS，导出运行时会 404。改 raw 后产物 3.2MB、零外部资源。`ai/assets.d.ts` 补 `*?raw` 声明。
3. `buildHandler.ts` 的 `BUILD_TIMEOUT_MS` 120s → 300s：实测该页 iife 构建 150~177s，旧超时会把「能成功的构建」杀掉，同样报 500。

**验证**：`ENTRY_KEY=... npx vite build` 成功（150s / 3.24MB / gzip 952KB）；重启 dev server 后 `GET /build/prototypes/ai-material-price-governance.js` 返回 200（177s / 3.36MB）；真实浏览器（CDP + 无头 Chrome）直接 import `ai/extract.ts` 解析示例文件：xlsx 1 表 11 行表头正确，PDF 走 blob worker 正常打开（扫描件 → scan:true）；页面渲染正常无报错。E2E 脚本 `temp/verify-extract-static.mjs`。

**结论/约定**：本项目原型页面**禁止动态 import()**，否则该页面导出必失败（只有它自己构建会挂，dev 模式察觉不到）。

## 修复「导出后 AI 拆解失败」

**用户判断**：以为是 AI 配置没写进文件。实际 `ai/config.ts` 的 `DEFAULT_AI_CONFIG` 早就写死了（页面配置面板里 baseUrl/model/key 都在），配置不是原因。

**真实原因**：`vite-plugins/llmProxyPlugin.ts` 只做转发，**一个 CORS 响应头都没设**（预检 OPTIONS 返 204 也无头）。导出后原型运行在 Axure / file:// 等其它源上：
1. 相对路径 `/llm-proxy/chat/completions` 打到了导出宿主（不是 dev server）→ 404；
2. 即使写绝对地址，跨源也会被浏览器 CORS 拦掉 → `Failed to fetch`；
3. 直连网关本身无 CORS → 同样失败。

实测证据：curl 带 `Origin` 打代理，POST 返回 200 且响应头里无 `Access-Control-Allow-Origin`；用 127.0.0.1:51799 的测试页（异源）同时测直连与跨域代理，两者都 `Failed to fetch`。

**修复**
1. `llmProxyPlugin.ts`：所有响应（含 OPTIONS / 错误分支）统一加 `Access-Control-Allow-Origin: *` 等头；新增 `GET /llm-proxy/health` 返回 `{ok:true}` 作为探针。
2. `ai/llm.ts`：代理地址改为自动探测——先同源，再依次试 `http://localhost|127.0.0.1:51720~51724` 的 `/llm-proxy/health`，命中后缓存；错误分两类：`TransportError`（连不上→换通道）和 `ApiError`（连上了但上游报错→直接抛，不重复烧 token）；失败提示里写明「导出件同样依赖本机 dev server」。
3. `ImportPage.tsx`：模型配置面板加「测试连接」按钮（一次 chatCompletion 自检），保存/恢复默认时 `resetProxyCache()`；配置说明文案同步更新。

**验证**
- 异源页面（`http://127.0.0.1:51799`）→ health 200、跨域 POST 200 流式、`chatCompletion()` 返回 "OK"（即导出场景等价可用）。
- 页面上点「测试连接」→ 提示「连接正常，模型已回复：好的」。
- `tsc` 本目录 0 错误；重新 iife 构建成功（158s / 3.24MB），产物含 `/llm-proxy/health`、`51721` 等新逻辑，零外部资源。

**已知限制**：导出件要求本机 dev server 在线；若导出宿主是 https 页面，浏览器会拦 http 代理（混合内容）。要真正离线/异地可用，需把代理部署到公网。

## 入库审核区分「新增建档 / 修改已有物料」（同步治理台）

**需求**：审核时要能分出这次是新增还是修改——专家组装时完全可能发现有相同商品，只是改属性值 / 新增属性 / 加同义词。治理台与入库审核都要同步。

**核心设计**
- `MaterialSubmission` 加 `changeType: 'new' | 'update'`、`targetStandardKey / targetStandardCode / targetStandardName`、`changes: SubmissionChange[]`。
- `SubmissionChange.kind` 四类：`value`（改值，带 before/after）、`add-atom`（新增属性）、`atom-synonym`（属性同义词）、`name-synonym`（商品叫法）。
- `similar.ts` 新增三个纯函数，治理台与审核页共用：
  - `diffStandardChanges(atoms, synonyms, standard)`：属性名按「当前名 + 该属性同义词 + defaultAtomSynonyms」归一后匹配标准侧；**跳过品类**（品类在 category 路径里）；**提交值为空视为「本次不改这项」**，不会清空标准库值；同义词只报「标准侧还没有的」。
  - `summarizeChanges` / `describeChanges`：一句话摘要「改值 N 项 · 新增属性 N 项 · 新增历史叫法 N 条」。
  - `mergeStandard(standard, atoms, synonyms, today)`：只合并 attributes / synonyms / attributeSynonyms + 刷新 updatedAt，编码名称品类价格全保留。
- 治理台关联表 `materialLink: Record<materialKey, standardKey>` 进 localStorage；`linkStandard(key|null)` 写/删。diff 不存，每次按最新标准实时算；提交时把结果快照进 `changes`。
- `reviewSubmission` approve 分叉：有 target → `mergeStandard`（`standardCount` 不变、不改 code/name/category/prices）；无 → 新建（`STD-AI-` +1）。两路都 `pendingCount-1`、`confirmedKeys` 追加。
- 审核列表加「提交方式」列（新增建档蓝 / 修改已有紫 + 目标编码 + N 项变更）、第二组 Segmented 按方式筛选、KPI 第四格拆「新增 N · 修改 N」。
- 审核详情加「本次变更」四列表（变更类型 / 属性 / 标准库现值 / 本次提交），组装结果行带 `改/新/同` 标记与「（原 xxx）」；相似卡在修改模式改成「打补丁、不会重复建档」；主按钮变「通过并合并」。
- 演示种子三条：新增待审核（m2）、新增已驳回（m3）、**修改 s2 待审核（m1，`sub-seed-3`）**；初始游标落 2（m3），一进工作台就是「驳回后重新提交」。

**坑/约定**
- **种子提交单的 atoms 必须与治理台那条 material 的数据一致**，否则治理台 banner 的 diff 与审核详情对不上（最初 m1 只写 5 项、提交单写 6 项，摘要差一条）。
- **`materialLink` 要从种子提交单反推**（`deriveMaterialLink`），只写 `submissions` 不写 link 会让治理台显示「未关联」而审核页显示「修改已有」，自相矛盾。

- 筛选栏放两组 Segmented 后搜索框会被压窄：`.pg-filter-search { flex: 1 1 280px }`，并在 ≤1200px 隐藏排序提示。
- 变更明细里一串 tag 用 `display:flex; gap:6px` + `margin-inline-end: 0`，不要只靠 tag 自带 margin。

## 采购清单「参考价」列 + 新增二级菜单「价格分析」

**需求（原话）**
> 编制采购清单页，其中的清单列加一列 参考价，填入模拟数据。另外建一个二级菜单页面，价格分析（参考截图：采购金额走势 / 区域分布 / 金额占比 / 数据详情）。用于展示这个商品过去的招采情况、签订合同的情况，和参考价联动，可以在参考价列除了价格展示外，还有查看详情跳转到这个页面来。

**核心设计**
- **单一数据源**：`analysisData.refPriceOf(key, unit)` 是参考价的唯一出口，采购清单行与价格分析页都调它；`refPriceSeed` 里 12 条标准物料的参考价与 `initialPrices` 的历史成交价对齐（3860 的钢筋两边必须一致）。未登记物料用哈希种子按计价单位量级生成，同一物料永远同一个价。
- **确定性伪随机**：`hashText`（FNV-1a）+ `mulberry32`，种子取标准物料编码。`buildAnalysis(subject, filter)` 生成近 24 个月每月 5~8 条 + 更早 16 条合同，**所有 KPI / 图表 / 明细表都从这一份合同集聚合**，所以「区域占比合计 100%」「明细条数 = 累计签订合同数」永远成立。
- **工程局 / 区域按序号轮转分配**，不是随机：纯随机会让「按单个工程局筛选」时某些月份一张合同都没有，走势图出现空洞（第一版就踩了，缺口前后折线还一头扎到 0）。
- 单价随距今年限缓慢上抬（每年 -3% 历史折价 + ±4% 个案波动），年度图才是温和上行线。
- **清单参考价列**插在「报价依据」与「含税单价」之间（依据 → 参考价 → 我的报价，比的逻辑才顺）：第一行金额+单位+相对报价偏离（高于用暖色 / 低于用绿色 / 持平灰），第二行日期+样本数+「查看详情 →」。

## 物料映射（`material-mapping` + 隐藏页 `mapping-detail`）

**目标**：把历史招标清单里的非标写法认到标准物料上，历史成交价才能按标准口径复用。一条标准物料 ← 多条历史写法（**一对多**），一条清单项 → 至多一条标准物料。

**打分（`recommendStandards`，纯本地、不依赖模型）**
```ts
const coverage = pairs.length ? matchedCount / pairs.length : 0;
const attrRatio = avgRatio * (0.7 + 0.3 * coverage);   // 只在双方都声明的属性上算相似度
const base = attrRatio*0.62 + nameRatio*0.18 + (synonymHit?0.1:0) + (categoryHit?0.1:0);
const strong = mismatchCount===0 && matchedCount>0 && (pairs.length<=1 || matchedCount>=2);
score = min(99, round(base*100) + (strong?10:0));      // 取前 4，≥35 分；AUTO_MAP_THRESHOLD=68
```
**踩过的坑**：最早把「标准侧多出的属性」放进分母当惩罚、且 `extras===0` 才给强证据分 → Φ25 只有 60 分、08812 十二条只映射上一条。标准侧规格更全本来就是好事，**不能惩罚**。改成上式后 Φ25 落到 80~90 分区间。

**规格型号三来源**（对上用户「默认帮你解析、你也可以改」）：`standard 沿用` / `ai 解析`（`parseBidSpec` 按品类抠，解析不出就**返回空**，不编）/ `manual 手工`。确认前拦住空行，提交与批量确认时**过滤空 label/value**，否则空行会卡死「这条没填完整」。

**统计口径**：`projectStats.amount` 只算 `confirmed && standardKey` —— 待复核是建议、`by:'new'` 还没进标准库，都不能算可复用历史价；进度条用 `(done+new)/total`，「转治理建档」算已处理。

**交互要点**
